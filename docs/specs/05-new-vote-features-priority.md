## 현황 요약

### HotPick 현재 투표 구조

| 항목      | 현재 상태                                  |
| --------- | ------------------------------------------ |
| 질문 구조 | 이지선다 (2개 선택지) 고정                 |
| 옵션 UI   | 이미지 + 제목 (옵션마다 이미지 필수)       |
| 묶음 구조 | 5개 질문 = 1 트렌드 (고정, 단일 투표 불가) |
| 결과 방식 | 즉시 득표율 공개 + 6가지 유형 분류         |
| 시간 요소 | 없음 (상시 투표 가능)                      |
| 분류 체계 | 없음 (생성일 기준 정렬만 존재)             |
| 실시간성  | 없음 (투표 시점의 스냅샷만 표시)           |

### 현재 핵심 페인포인트

1. **콘텐츠 생성 비용이 높다** — 옵션마다 이미지가 반드시 필요하여, 투표 1개를 만들기 위해 최소 2장의 이미지를 준비해야 한다. 5개 묶음이면 최소 10장. 이것이 콘텐츠 양산의 가장 큰 허들이다.
2. **단일 투표가 불가능하다** — 반드시 5개를 묶어야 하나의 트렌드가 되므로, "지금 바로 이 질문 하나만 던지고 싶다"는 니즈를 충족할 수 없다. 시의성 있는 이슈에 빠르게 대응할 수 없다.

### Polymarket에서 참고 가능한 핵심 요소

| 요소                | Polymarket                 | HotPick 적용 가능성 |
| ------------------- | -------------------------- | ------------------- |
| 다양한 질문 유형    | Yes/No, Either/Or, Up/Down | 높음                |
| 카테고리컬 마켓     | 3개 이상 선택지            | 높음                |
| 카테고리 분류       | 정치/스포츠/문화 등        | 높음                |
| 시계열 시각화       | 시간별 확률 변화 차트      | 중간                |
| 마켓 상태 관리      | Open/Closed/Resolved       | 높음                |
| 단일 마켓 독립 운영 | Single-Outcome Market      | 높음                |
| 이벤트 그룹핑       | 하나의 이벤트 → 복수 마켓  | 중간                |

## 작업 프로세스 원칙

모든 기능은 서버(API/DB) 작업이 수반된다. 우리의 역할은 프론트엔드 개발 + 서버팀에 전달할 API 스펙 문서 작성이다.

각 기능별 작업은 다음 순서로 진행한다:

```
1. API 스펙 문서 작성 → 서버팀 전달
2. 서버 API 개발 완료 대기
3. 프론트엔드 UI/UX 개발
4. API 연동 및 통합 테스트
```

따라서 아래 각 기능 설명에는 **서버 전달 API 스펙**을 함께 명시한다.

## 투표 UI 유형 체계 (신규 개념)

신규 기능에 앞서, 투표를 UI 형태에 따라 유형화하는 체계가 필요하다.

### 유형 정의

| 유형명      | 코드    | 메인 이미지               | 옵션 구성                   | 용도                                     |
| ----------- | ------- | ------------------------- | --------------------------- | ---------------------------------------- |
| 이미지 투표 | `IMAGE` | 없음 (옵션 이미지가 대체) | 이미지 + 텍스트 (현재 방식) | "바삭 vs 촉촉" 같은 시각적 대비          |
| 텍스트 투표 | `TEXT`  | 1장 (질문 대표 이미지)    | 텍스트만                    | "최고의 치킨 브랜드는?" 같은 텍스트 중심 |

### 텍스트 투표 UI 예시

```
┌──────────────────────────────────┐
│                                  │
│        [메인 이미지 1장]          │
│                                  │
├──────────────────────────────────┤
│     최고의 치킨 브랜드는?         │
├──────────────────────────────────┤
│  ┌────────────────────────────┐  │
│  │      ① BBQ               │  │
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │      ② 교촌치킨            │  │
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │      ③ BHC               │  │
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │      ④ 굽네치킨            │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

**핵심 효과**: 이미지 1장 + 텍스트 옵션만으로 투표 생성 가능 → 콘텐츠 생성 비용 대폭 절감

#### 1. 단일 투표 — Single

**Polymarket 참고**: Single-Outcome Market — 하나의 독립된 질문이 곧 하나의 마켓

**현재 한계**: 반드시 5개 질문을 묶어야 트렌드가 되므로, 시의성 있는 이슈에 빠르게 대응할 수 없다. 트렌드 1개를 만들려면 5개 질문 + 10장 이상의 이미지가 필요하여 콘텐츠 발행 주기가 느리다. 또한 사용자 입장에서도 5개를 모두 완료해야 결과를 볼 수 있어 이탈률이 높을 수 있다.

**제안 내용**:

- 트렌드(묶음)와 독립된 **단일 투표 엔티티** 신설
- 1개 질문 = 1개 Single 투표
- 투표 UI 유형 선택 가능: 이미지 투표(IMAGE) 또는 텍스트 투표(TEXT)
- 선택 즉시 결과 확인 (기존 카드 뒤집기 방식 동일)
- 결과 페이지 없이 투표 카드 내에서 결과 확인 완료
- 유형 분류 없음 (단일 투표이므로 성향 분석 불필요)
- Main 페이지에서 **별도 탭**으로 독립 노출 (탭 분리 방식 채택 — 혼합 피드 대비 콘텐츠 비대칭, 참여 깊이 차이, 산업 표준 부합)
- 트렌드 탭과 Single 탭 각각 독립적 정렬/필터/페이지네이션

**Single 카드 UI (Single 탭)**:

```
┌──────────────────────────────────┐
│ [HOT]                    D-2    │
│                                  │
│     [메인 이미지 or 옵션 이미지]  │
│                                  │
│   "짜장면 vs 짬뽕, 당신의 선택?" │
│                          1.2K명  │
└──────────────────────────────────┘
```

**도입 효과**: 콘텐츠 발행 속도 극대화, 시의성 대응력 확보, 사용자 진입 장벽 대폭 감소, 스낵형 소비 패턴 지원

**개발 난이도**: ★★★☆☆

**프론트엔드 작업**:

- Single 전용 VoteCard 컴포넌트 개발
- Main 페이지 탭 네비게이션 + Single 탭 콘텐츠 렌더링
- Single 전용 투표/결과 인라인 UI
- Admin: Single 생성/수정 폼 개발

**서버 전달 API 스펙**:

> Single은 별도 엔티티가 아닌, HotPick(type=SINGLE) + Election 1개 조합으로 구현한다.
> 따라서 기존 HotPick CRUD API에 `type` 필터를 추가하는 방식으로 처리하며, 별도의 Single 전용 API는 필요하지 않다.
> 상세 API 스펙은 `docs/api/election-crud-api-request.md` 참조.

**HotPick(SINGLE) 구성**:

```
HotPick (type: SINGLE) {
  id: number
  alias: string
  title: string                    // 질문 텍스트
  type: "SINGLE"                   // 핫픽 유형
  categoryCode?: string            // 카테고리 (P0-4와 연계)
  deadline?: datetime              // 마감일 (P0-3과 연계)
  status: "OPEN" | "CLOSED"
  electionIds: [string]            // Election 1개
  totalVotes: number
  createdAt: datetime
}
```

#### 2. 텍스트 투표 UI 유형 도입

**현재 한계**: 모든 옵션에 이미지가 필수이므로, 하나의 투표를 만들기 위한 리소스가 과다하다. "최고의 라면은?"이라는 질문에 라면 브랜드마다 사진을 준비해야 하는 것은 비효율적이다.

**제안 내용**:

- 기존 투표(트렌드 내 Item)에도 `voteType` 필드 추가
- `IMAGE`: 기존 방식 유지 (옵션마다 이미지 + 텍스트)
- `TEXT`: 메인 이미지 1장 + 옵션은 텍스트만
- 하나의 트렌드 내에서 IMAGE/TEXT 혼용 가능
- Admin 폼에서 투표 유형 선택 UI 추가

**TEXT 유형 VoteCard 앞면**:

```
┌──────────────────────────────────┐
│                                  │
│         [메인 이미지 1장]         │
│                                  │
│     올해 최고의 라면은?           │
├──────────────────────────────────┤
│  ┌─────────────────────────────┐ │
│  │       신라면                 │ │
│  └─────────────────────────────┘ │
│  ┌─────────────────────────────┐ │
│  │       진라면                 │ │
│  └─────────────────────────────┘ │
└──────────────────────────────────┘
```

**TEXT 유형 VoteCard 뒷면 (결과)**:

```
┌──────────────────────────────────┐
│                                  │
│         [메인 이미지 1장]         │
│                                  │
│     올해 최고의 라면은?           │
├──────────────────────────────────┤
│  ┌─────────────────────────────┐ │
│  │  신라면     ████████░  62%  │ │
│  └─────────────────────────────┘ │
│  ┌─────────────────────────────┐ │
│  │  진라면     ███░░░░░░  38%  │ │ ← 내 선택 ✓
│  └─────────────────────────────┘ │
└──────────────────────────────────┘
```

**도입 효과**: 콘텐츠 생성 비용 50% 이상 절감, 콘텐츠 발행 빈도 증가 가능, 텍스트 중심 질문(브랜드 선택, 의견 투표 등)에 최적화

**개발 난이도**: ★★☆☆☆

**프론트엔드 작업**:

- VoteCard 내 voteType 분기 렌더링
- TEXT 유형 전용 옵션 리스트 컴포넌트
- TEXT 유형 결과 표시 (프로그레스 바 + 득표율)
- Admin: 투표 유형 선택 토글 + 조건부 폼 필드

**서버 전달 API 스펙**:

| API                  | 변경 내용                                         |
| -------------------- | ------------------------------------------------- |
| Election 엔티티 수정 | `voteType: "IMAGE" \| "TEXT"` 필드 추가           |
| Election 엔티티 수정 | `mainImageUrl?: string` 필드 추가 (TEXT 유형용)   |
| Option 엔티티 수정   | `imageUrl`을 optional로 변경 (TEXT 유형은 불필요) |
| 트렌드 생성/수정 API | 기존 API에 voteType 관련 필드 반영                |

**Election 엔티티 변경사항**:

```
Election {
  id: string
  title: string
  voteType: "IMAGE" | "TEXT"       // 🆕 투표 UI 유형
  mainImageUrl?: string            // 🆕 TEXT 유형 메인 이미지
  options: [
    {
      id: string
      title: string
      imageUrl?: string            // 변경: 필수 → 선택 (TEXT면 불필요)
    }
  ]
}
```

#### 3. 투표 마감 시스템 (Time-limited Voting)

**Polymarket 참고**: Market States — Open/Closed/Resolved

**현재 한계**: 모든 트렌드가 상시 열려 있어서 긴급감이 없다. "이번 주 트렌드"라고 해도 사용자가 언제든 투표 가능하여 FOMO가 약하다.

**제안 내용**:

- 트렌드/Single에 마감일(deadline) 필드 추가
- 상태 관리: 진행중(OPEN) → 마감(CLOSED)
- 마감 카운트다운 표시: "마감까지 2일 3시간"
- 마감된 투표는 투표 불가, 결과 열람만 가능
- PollCard에 마감 임박 배지 추가 (예: "D-1", "마감임박🔥")
- deadline이 null이면 기존처럼 상시 투표 가능

**도입 효과**: "지금 안 하면 못 한다" FOMO 극대화, 주간 사이클 강화, 재방문률 증가

**개발 난이도**: ★★☆☆☆

**프론트엔드 작업**:

- PollCard/SingleCard에 마감 카운트다운 UI
- 마감 임박 배지 컴포넌트 (D-3 이내)
- 마감된 투표 비활성 처리 (투표 불가, 결과만 표시)
- Admin: 마감일 DateTimePicker 추가

**서버 전달 API 스펙**:

| API               | 변경 내용                                         |
| ----------------- | ------------------------------------------------- |
| Trend 엔티티 수정 | `deadline?: datetime` 필드 추가                   |
| Trend 엔티티 수정 | `status: "OPEN" \| "CLOSED"` 필드 추가            |
| Single (HotPick)  | 위 Single 스펙에 이미 포함                        |
| 목록 조회 API     | `status` 필터 파라미터 추가                       |
| 마감 처리         | 서버 스케줄러로 deadline 도래 시 자동 CLOSED 전환 |

#### 4. 카테고리 분류 시스템

**Polymarket 참고**: Politics/Sports/Crypto/Culture 등 카테고리별 탐색

**제안 내용**:

- 트렌드와 Single 모두에 동일한 카테고리 체계 적용

**도입 효과**: 사용자 탐색 경험 개선, 관심 분야 중심 소비 가능, 콘텐츠 정체성 강화

**개발 난이도**: ★★☆☆☆

**프론트엔드 작업**:

- Main 페이지 카테고리 필터 칩 UI
- PollCard/SingleCard에 카테고리 태그 표시
- Admin: 카테고리 선택 드롭다운

### 🟡 P1 — 단기 도입 (경험 강화)

#### 5. 다중 선택지 투표 (Categorical Vote)

**Polymarket 참고**: Categorical Market — 3개 이상 옵션 중 택 1

**현재 한계**: 모든 질문이 2개 선택지로 고정되어 콘텐츠 다양성이 부족하다. "최고의 치킨 브랜드는?"처럼 3~4개 선택지가 자연스러운 질문을 억지로 A vs B로 쪼개야 한다.

**제안 내용**:

- 선택지 수를 2~4개로 확장
- IMAGE 유형 (2개): 기존 좌우 분할 UI 유지
- IMAGE 유형 (3~4개): 그리드 배치 또는 세로 리스트
- TEXT 유형 (2~4개): 세로 리스트 (자연스럽게 확장)
- 결과 화면에서 각 선택지별 득표율 프로그레스 바 표시
- 6가지 유형 분류 로직 수정: "1위 선택지를 골랐는가" 기준으로 전환
- 트렌드 내 Item과 Single 모두에 적용

**도입 효과**: 콘텐츠 기획의 자유도가 대폭 확대, "최고의 ○○" 류 인기 포맷 활용 가능

**개발 난이도**: ★★★☆☆

**프론트엔드 작업**:

- VoteOptionCard 레이아웃 분기 (2개: 좌우, 3~4개: 그리드/리스트)
- 결과 프로그레스 바 다중 옵션 대응
- 유형 분류 로직 수정 (50% 기준 → 1위 기준)
- Admin: 옵션 개수 동적 추가/삭제 UI

**서버 전달 API 스펙**:

| 선거 검증 로직 수정  | "선택지가 2개인 선거만" → "선택지가 2~4개인 선거"   |

#### 6. 실시간 참여율 변화 시각화

**Polymarket 참고**: 시계열 차트 — 시간에 따른 확률 변동 그래프

**현재 한계**: 현재 득표율만 정적으로 표시되어, 투표가 시간에 따라 어떻게 변화했는지 알 수 없다.

**제안 내용**:

- Result 페이지의 MY PICK HISTORY에 트렌드 차트 포함

**도입 효과**: 투표의 역동성 부여, 재방문 동기 생성, SNS 공유 소재 확대

**개발 난이도**: ★★★☆☆

**프론트엔드 작업**:

#### 7. 예측형 투표 (Prediction Vote)

**Polymarket 참고**: Binary Market의 이벤트 발생 예측 구조

**현재 한계**: 모든 투표가 "취향/의견" 기반이라 정답이 없다. 정답이 있는 예측형 투표를 추가하면 재미 요소가 크게 확장된다.

**제안 내용**:

- 트렌드/Single에 `voteMode` 필드 추가: `OPINION`(의견) vs `PREDICTION`(예측)
- PREDICTION 모드:
  - 마감일 필수 (마감 후 정답 공개)
  - 관리자가 마감 후 정답 옵션을 지정
  - 사용자에게 "적중/빗나감" 피드백
  - PollCard에 "예측" 배지 표시
- 예시: "이번 주 박스오피스 1위는?", "다음 경기 승자는?"

**도입 효과**: 정답 확인 욕구로 재방문 유도, "나 맞췄다!" 공유 바이럴, 게임화 요소 강화

**개발 난이도**: ★★★★☆

**프론트엔드 작업**:

- 예측 배지 컴포넌트
- 마감 후 정답 공개 UI (정답 옵션 하이라이트)
- 사용자별 적중/빗나감 표시
- Admin: 정답 지정 UI (마감 후 정산 기능)

**서버 전달 API 스펙**:

| API                | Method | 경로                                | 설명               |
| ------------------ | ------ | ----------------------------------- | ------------------ |
| 정답 지정          | PUT    | `/api/admin/elections/{id}/resolve` | 정답 optionId 지정 |
| 정답 지정 (Single) | PUT    | `/api/admin/hotpick/{id}/resolve`   | 정답 optionId 지정 |

**엔티티 추가 필드**:

```
Election / HotPick {
  voteMode: "OPINION" | "PREDICTION"   // 🆕
  resolvedOptionId?: string             // 🆕 정답 옵션 (관리자 지정)
  resolvedAt?: datetime                 // 🆕 정산 시각
}
```

#### 8. 방향성(Over/Under) 투표

**Polymarket 참고**: Up/Down 질문 — 수치 기준 상회/하회

**현재 한계**: 질문이 "A vs B" 구조만 가능하여, 수치 기반 예측이 불가능하다.

**제안 내용**:

- 새로운 voteType: `OVER_UNDER`
- 기준점(threshold) + Over/Under 2택 구조
- 예시: "이번 주 '오징어게임2' 시청시간 1억 넘길까? O/U"
- 예측형(PREDICTION)과 결합하여 실제 수치 공개 가능
- UI: 기준점 강조 + 상/하 버튼 또는 좌/우 분할

**도입 효과**: 스포츠, 경제, 엔터테인먼트 등 수치 기반 콘텐츠 영역 확장

**개발 난이도**: ★★★☆☆

**프론트엔드 작업**:

- Over/Under 전용 VoteCard UI
- 기준점 강조 표시 + 결과 시 실제 수치 표시

**서버 전달 API 스펙**:

| API                    | 변경 내용                                         |
| ---------------------- | ------------------------------------------------- |
| Election/HotPick 엔티티 | `voteType`에 `"OVER_UNDER"` 추가                  |
| Election/HotPick 엔티티 | `threshold?: number` 필드 추가 (기준점)           |
| Election/HotPick 엔티티 | `actualValue?: number` 필드 추가 (실제 결과 수치) |

#### 9. 유연한 묶음 구조 (Flexible Bundle)

**Polymarket 참고**: Multi-Outcome Market — 하나의 이벤트에 복수 마켓

**현재 한계**: 반드시 5개 질문이 하나의 트렌드를 구성해야 한다. 주제에 따라 3개가 적절하거나 7개가 필요할 수 있다.

**제안 내용**:

- 질문 수를 3~7개 범위로 유연하게 설정 가능
- 6가지 유형 분류 로직을 비율 기반으로 변경 (1위 선택 비율)
- 대중성 지수 계산은 동일 (평균 득표율)
- Admin에서 질문 수 자유 설정

**도입 효과**: 콘텐츠 기획 유연성 확보, 짧은 투표(3개)로 진입장벽 낮추기 가능

**개발 난이도**: ★★★☆☆

**프론트엔드 작업**:

- ProgressBar 동적 렌더링 (5개 고정 → N개 동적)
- 유형 분류 로직 일반화
- Admin: 선거 연결 개수 제한 변경 (5개 고정 → 3~7개)

**서버 전달 API 스펙**:

| API                 | 변경 내용                                      |
| ------------------- | ---------------------------------------------- |
| Trend 생성/수정 API | `electionIdList` 검증: 정확히 5개 → 3~7개 허용 |
| Trend 엔티티        | 변경 없음 (배열 크기만 유연해짐)               |

#### 10. 투표 트렌드 대시보드
